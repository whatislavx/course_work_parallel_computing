# Результати бенчмарків (TCK-029, TCK-030, TCK-031)

## Умови (TEST-PERF-01…03, OQ-17, OQ-25)

- Машина: 2 логічних ядра (`nproc=2`); ОС і апаратна модель не зафіксовані в цій сесії.
- Збірка: CMake `Release`, `-O3 -DNDEBUG`, GCC; сервер запущено нативно, **не в Docker** (демон недоступний).
- Датасет: синтетичний корпус, 10 500 документів, 1.1 ГБ, seed 20261108 (`scripts/generate_dataset.py`). Джерело ще не затверджене (OQ-01).
- Ollama недоступна (fallback розширення запиту, A1).
- Прогрів: один запуск перед вимірами. Повторів: **3** для побудови (рекомендація специфікації — 5; скорочено через тривалість ~20 с на запуск), **2000** запитів на рівень для навантаження.
- Набір потоків: 1, 2, 4. Для C = 2 критерій NFR-001 — `T(2) < T(1)`; 4 показує насичення.

## TCK-031: аналіз (без профайлера)

- **Побудова.** Прискорення 1.45 при 2 потоках відповідає 2 ядрам; при 4 потоках часу більше, ніж при 2. Причина найімовірніше в CPU-обмеженні та накладних витратах синхронізації. Це **гіпотеза**: `perf` не встановлений, профілювання не виконано.
- **Пам'ять.** Пік RSS 3.5–5.5 ГБ для корпусу 1.1 ГБ. Зростання з потоками пояснюється паралельними буферами. Ця гіпотеза також не перевірена профайлером.
- **Пошук.** Throughput зростає до ~390 зап/с і далі майже не росте, затримка росте майже лінійно від K. Це ознака насичення двох ядер, а не блокування.

Профайлер (`perf` або `gprof`) і повна перевірка гіпотез — відкритий пункт.
