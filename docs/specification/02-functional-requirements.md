# 02. Функціональні вимоги

Формат запису: кожна вимога атомарна, описує спостережувану поведінку і має стабільний ID. Поля «Пріоритет» і «Походження» пояснено в `01-overview.md` §1.9. Посилання на BDD-сценарії та тести: `10-requirements-traceability.md`, матриця B.

Скорочення полів: **Опис**, **Обґрунтування**, **Джерело**, **Пріоритет / Походження**, **Передумови**, **Тригер**, **Очікувана поведінка**, **Постумови**, **Пов'язані**, **Залежності**, **Критерії прийняття (AC)**, **Перевірка** (T — тест, I — інспекція, D — демонстрація, A — аналіз).

## Група HLT. Стан сервера

### FR-001. Перевірка стану сервера
- **Опис:** Система надає ендпоінт перевірки стану, який повідомляє, що сервер працює.
- **Обґрунтування:** Обов'язковий критерій «Docker Compose» і першої атестації.
- **Джерело:** SRC-A §Основні вимоги п.2, п.4; §Специфікація REST API; SRC-SYL §Критерії («Docker Compose»), §Перша атестація.
- **Пріоритет / Походження:** Must / M.
- **Передумови:** Процес сервера запущено.
- **Тригер:** Клієнт надсилає `GET /api/health`.
- **Очікувана поведінка:** Сервер відповідає HTTP 200 з JSON, де `status` = `"ok"`.
- **Постумови:** Стан системи не змінюється.
- **Пов'язані:** FR-002, NFR-010, NFR-011.
- **Залежності:** —
- **AC:** AC-001.1 код 200; AC-001.2 тіло — валідний JSON з полем `status` типу string і значенням `"ok"`; AC-001.3 відповідь не залежить від того, чи побудовано індекс.
- **Перевірка:** T.

### FR-002. Звіт про доступність Ollama
- **Опис:** Відповідь перевірки стану містить булеве поле `ollama`, що відображає доступність сервісу Ollama на момент запиту.
- **Обґрунтування:** Контракт SRC-A; дозволяє клієнтам і перевіряльнику знати, чи працюватиме query expansion.
- **Джерело:** SRC-A §Специфікація REST API (`"ollama": true|false`).
- **Пріоритет / Походження:** Must / M. Семантика «доступний» — P (OQ-13).
- **Передумови:** FR-001.
- **Тригер:** `GET /api/health`.
- **Очікувана поведінка:** `ollama` = `true`, якщо Ollama відповіла на перевірку протягом тайм-ауту перевірки стану; інакше `false`. Пропозиція: «доступна» = HTTP-відповідь Ollama успішна та налаштована модель присутня (OQ-13). Код відповіді залишається 200 в обох випадках.
- **Постумови:** —
- **Пов'язані:** FR-019, FR-021, NFR-008, NFR-020.
- **Залежності:** FR-001.
- **AC:** AC-002.1 поле `ollama` присутнє, тип boolean; AC-002.2 при працюючій Ollama з налаштованою моделлю — `true`; AC-002.3 при зупиненій Ollama — `false` і код 200; AC-002.4 відповідь повертається не пізніше тайм-ауту перевірки (значення — OQ-14).
- **Перевірка:** T.

## Група IDX. Побудова індексу

### FR-003. Побудова інвертованого індексу з текстових файлів
- **Опис:** За запитом система будує інвертований індекс з усіх текстових документів налаштованого каталогу датасету.
- **Обґрунтування:** Критерій «Інвертований індекс»; основна функція.
- **Джерело:** SRC-A §Основні вимоги п.3, п.4; SRC-SYL §Критерії («POST /api/index будує індекс з текстових файлів»).
- **Пріоритет / Походження:** Must / M.
- **Передумови:** Каталог датасету налаштовано (NFR-019) і змонтовано в контейнер (OQ-23); не триває інша побудова (FR-009).
- **Тригер:** `POST /api/index`.
- **Очікувана поведінка:** Система виявляє всі документи в каталозі (рекурсивно, пропозиція OQ-18), зчитує, токенізує та вносить у новий індекс. Після успішного завершення новий індекс стає активним (FR-008). Порожній каталог дає індекс з 0 документів (P, OQ-22). Документ, який не вдалося прочитати, не потрапляє в індекс, а пропуск логується з назвою файлу (P, OQ-19). «Не вдалося прочитати» (P, OQ-19) — це помилки файлової системи під час відкриття або читання (файл зник після переліку, немає прав, помилка вводу-виводу) і некоректний UTF-8. Будь-який інший виняток під час токенізації чи вставки — це аварійне завершення задачі за FR-042. Якщо каталог відсутній або недоступний, побудова завершується помилкою, а попередній активний індекс зберігається.
- **Постумови:** Активний індекс містить постинги для всіх успішно прочитаних документів.
- **Пов'язані:** FR-004…FR-010, NFR-005, NFR-014.
- **Залежності:** CON-004, CON-015, NFR-019.
- **AC:** AC-003.1 для тестового корпусу з K документів `documents_indexed` = K; AC-003.2 за `SEARCH_TOP_K` ≥ K кожен терм кожного документа корпусу знаходиться пошуком (FR-013), а набір знайдених документів збігається з еталоном FIX-02; AC-003.3 відсутній каталог → помилка 500 з форматом помилки (06 §2.4), попередній індекс доступний для пошуку; AC-003.4 порожній каталог → 200, `documents_indexed` = 0; AC-003.5 нечитабельний файл виключено з підрахунку, у лозі є запис з його назвою.
- **Перевірка:** T.

### FR-004. Параметр кількості потоків
- **Опис:** Запит побудови приймає параметр `threads` — кількість робочих потоків для побудови.
- **Обґрунтування:** Критерій «Thread pool»: варіювання кількості потоків.
- **Джерело:** SRC-A §Основні вимоги п.3 («можливість варіювання кількості потоків»), п.4; SRC-SYL §Критерії («Параметр threads в POST /api/index»).
- **Пріоритет / Походження:** Must / M. Значення за замовчуванням — P (OQ-07).
- **Передумови:** —
- **Тригер:** `POST /api/index` з тілом `{ "threads": p }`.
- **Очікувана поведінка:** Побудова виконується пулом з рівно `p` робочих потоків. Якщо `threads` відсутній, тіло дорівнює `{}` або тіло порожнє, використовується значення за замовчуванням із конфігурації (P, OQ-07; пропозиція: кількість логічних процесорів). Тіло розбирається як JSON незалежно від заголовка `Content-Type` (P, OQ-11).
- **Постумови:** `threads_used` у статистиці = `p` (FR-010).
- **Пов'язані:** FR-006, FR-007, FR-010.
- **Залежності:** FR-003.
- **AC:** AC-004.1 після побудови з `threads: p` статистика повертає `threads_used: p` для p ∈ {1, 2, 4, 8}; AC-004.2 без `threads`, з тілом `{}` і з порожнім тілом без заголовка `Content-Type` — `threads_used` дорівнює налаштованому значенню за замовчуванням; AC-004.3 тіло `{"threads": 2}` із заголовком `Content-Type: application/x-www-form-urlencoded` приймається (200).
- **Перевірка:** T.

### FR-005. Відповідь на побудову індексу
- **Опис:** Після завершення побудови сервер повертає результат з полями `status`, `documents_indexed`, `time_ms`.
- **Обґрунтування:** Фіксований контракт SRC-A.
- **Джерело:** SRC-A §Специфікація REST API (`{ "status": "ok", "documents_indexed": 2000, "time_ms": 1234 }`).
- **Пріоритет / Походження:** Must / M. Синхронність і межі вимірювання часу — P (OQ-20).
- **Передумови:** FR-003.
- **Тригер:** Завершення побудови, ініційованої `POST /api/index`.
- **Очікувана поведінка:** Відповідь надсилається після завершення побудови (синхронно). `time_ms` — тривалість побудови в мілісекундах від початку виявлення документів до активації нового індексу (P, OQ-20), без часу обробки HTTP. Сервер не закриває з'єднання запиту побудови через власні тайм-аути читання/запису раніше, ніж мине `INDEX_REQUEST_TIMEOUT_MS` (конфігурація, NFR-019, OQ-20). Пропозиція (OQ-20): значення за замовчуванням — не менше 2·T(1) на бенчмарковому датасеті; README називає очікуваний T(1) і мінімальний тайм-аут клієнта.
- **Постумови:** —
- **Пов'язані:** FR-010.
- **Залежності:** FR-003.
- **AC:** AC-005.1 код 200; AC-005.2 `status` = `"ok"`; AC-005.3 `documents_indexed` — ціле ≥ 0; AC-005.4 `time_ms` — ціле ≥ 0; AC-005.5 жодних полів, крім перелічених; AC-005.6 [P, OQ-20] на бенчмарковому датасеті з p = 1: T(1) < `INDEX_REQUEST_TIMEOUT_MS`, і клієнт з тайм-аутом ≥ `INDEX_REQUEST_TIMEOUT_MS` отримує 200 (TEST-PERF-01).
- **Перевірка:** T.

### FR-006. Паралельне виконання побудови пулом потоків
- **Опис:** Робота з індексації (зчитування, токенізація, внесення постингів) розподіляється між робочими потоками власного пулу, кількість яких задає `threads`.
- **Обґрунтування:** Головний предмет дослідження; критерії «Thread pool» і «Паралельна структура даних».
- **Джерело:** SRC-A §Завдання, §Мета, §Основні вимоги п.3.
- **Пріоритет / Походження:** Must / M.
- **Передумови:** FR-004.
- **Тригер:** Старт побудови.
- **Очікувана поведінка:** Одночасно виконується до `p` задач індексації. Паралелізується саме індексація (токенізація і вставка постингів), а не лише зчитування файлів. Поведінку пулу визначають FR-036…FR-041; наслідок аварійного завершення задачі — FR-042.
- **Постумови:** Усі задачі побудови завершено; життєвий цикл пулу — за FR-036 і FR-040.
- **Пов'язані:** NFR-001, NFR-004…NFR-006, FR-042, CON-003, CON-004.
- **Залежності:** FR-004, FR-036, FR-037, FR-038.
- **AC:** AC-006.1 під час побудови з `threads: p` кількість одночасно активних робочих потоків пулу не перевищує `p` і досягає `p` хоча б раз при кількості задач ≥ p (тест з інструментованим пулом); AC-006.2 результат побудови з будь-яким p ідентичний послідовному (NFR-005).
- **Перевірка:** T, A (бенчмарк NFR-001).

### FR-007. Валідація параметра `threads`
- **Опис:** Некоректне значення `threads` відхиляється без запуску побудови.
- **Обґрунтування:** Явна обробка помилок вводу.
- **Джерело:** SRC-A не визначає; P (OQ-07, OQ-11).
- **Пріоритет / Походження:** Should / P.
- **Передумови:** —
- **Тригер:** `POST /api/index` з невалідним тілом.
- **Очікувана поведінка:** Відповідь 400 з форматом помилки (06 §2.4), якщо: тіло не є валідним JSON; тіло не є JSON-об'єктом; `threads` не є цілим числом (JSON-число з десятковою крапкою чи експонентою, наприклад `4.0`, вважається не цілим — P, OQ-07); `threads` < 1; `threads` > `MAX_INDEX_THREADS` (конфігурація, значення OQ-07). Активний індекс і статистика не змінюються.
- **Постумови:** Без змін.
- **Пов'язані:** FR-004.
- **Залежності:** FR-004.
- **AC:** AC-007.1 значення `0`, `-1`, `"four"`, `1.5`, `4.0`, `null`, `MAX_INDEX_THREADS+1` → 400 `invalid_threads`; AC-007.2 некоректний JSON → 400; AC-007.3 статистика до і після відхиленого запиту однакова.
- **Перевірка:** T.

### FR-008. Повторна побудова замінює активний індекс
- **Опис:** Повторний успішний запит побудови замінює активний індекс новим.
- **Обґрунтування:** Бенчмарк вимагає багаторазової побудови з різним p.
- **Джерело:** Випливає з SRC-A п.3 (варіювання потоків) і §Тестування (графік 1…N); семантика заміни — P (OQ-10).
- **Пріоритет / Походження:** Must / P.
- **Передумови:** Існує активний індекс.
- **Тригер:** Успішне завершення наступної побудови.
- **Очікувана поведінка:** Новий індекс атомарно стає активним; старий звільняється після завершення пошуків, що його використовують. Статистика оновлюється значеннями нової побудови.
- **Постумови:** Активний — лише новий індекс.
- **Пов'язані:** FR-010, FR-035.
- **Залежності:** FR-003.
- **AC:** AC-008.1 дві побудови поспіль (p=2, потім p=4) → `threads_used: 4`, `index_build_time_ms` = `time_ms` другої відповіді; AC-008.2 результати пошуку однакові після обох побудов на незмінному датасеті.
- **Перевірка:** T.

### FR-009. Відхилення побудови під час іншої побудови
- **Опис:** Якщо побудова вже триває, новий запит побудови відхиляється.
- **Обґрунтування:** Без цього правила поведінка невизначена; конкурентні побудови спотворюють заміри.
- **Джерело:** P (OQ-08).
- **Пріоритет / Походження:** Should / P.
- **Передумови:** Триває побудова.
- **Тригер:** Другий `POST /api/index`.
- **Очікувана поведінка:** Відповідь 409 з кодом помилки `index_build_in_progress`; поточна побудова продовжується без змін.
- **Постумови:** Без змін.
- **Пов'язані:** FR-003, NFR-010.
- **Залежності:** FR-003.
- **AC:** AC-009.1 другий запит під час побудови → 409, код `index_build_in_progress`; AC-009.2 перша побудова завершується з коректним результатом.
- **Перевірка:** T.

## Група STA. Статистика

### FR-010. Статистика індексу
- **Опис:** Система повертає статистику активного індексу: кількість документів, час останньої успішної побудови, кількість використаних потоків.
- **Обґрунтування:** Контракт SRC-A; критерій «Інвертований індекс».
- **Джерело:** SRC-A §Специфікація REST API (`GET /api/stats`); SRC-SYL §Критерії.
- **Пріоритет / Походження:** Must / M.
- **Передумови:** —
- **Тригер:** `GET /api/stats`.
- **Очікувана поведінка:** 200 з `documents`, `index_build_time_ms`, `threads_used` останньої успішної побудови.
- **Постумови:** —
- **Пов'язані:** FR-004, FR-005, FR-008, FR-011.
- **Залежності:** FR-003, FR-005.
- **AC:** AC-010.1 `documents` = `documents_indexed` останньої відповіді побудови; AC-010.2 `index_build_time_ms` = `time_ms` тієї ж відповіді; AC-010.3 `threads_used` = `threads` тієї ж побудови; AC-010.4 усі три поля — цілі ≥ 0; інших полів немає.
- **Перевірка:** T.

### FR-011. Статистика до першої побудови
- **Опис:** До першої успішної побудови статистика повертає нульові значення.
- **Обґрунтування:** Поведінка не визначена в SRC-A.
- **Джерело:** P (OQ-09).
- **Пріоритет / Походження:** Should / P.
- **Передумови:** Жодної успішної побудови з моменту старту.
- **Тригер:** `GET /api/stats`.
- **Очікувана поведінка:** 200 з `documents: 0`, `index_build_time_ms: 0`, `threads_used: 0`.
- **Постумови:** —
- **Пов'язані:** FR-010.
- **Залежності:** FR-010.
- **AC:** AC-011.1 одразу після старту — 200 і три нульові поля.
- **Перевірка:** T.

## Група SRC. Пошук за ключовими словами

### FR-012. Прийом пошукового запиту
- **Опис:** Система приймає пошуковий запит з полями `query` (рядок) і `mode` (рядок).
- **Обґрунтування:** Контракт SRC-A; критерій «Keyword search».
- **Джерело:** SRC-A §Основні вимоги п.4; §Специфікація REST API.
- **Пріоритет / Походження:** Must / M.
- **Передумови:** —
- **Тригер:** `POST /api/search`.
- **Очікувана поведінка:** Запит з валідними `query` і `mode` передається на пошук (FR-013). `mode: "keyword"` — пошук без розширення; `mode: "expanded"` — розширення запиту через Ollama (FR-019), потім пошук (рішення OQ-02, підтвердження викладача). Поле `mode` обов'язкове. Тіло розбирається як JSON незалежно від заголовка `Content-Type` (P, OQ-11).
- **Постумови:** —
- **Пов'язані:** FR-013, FR-016, FR-019.
- **Залежності:** CON-005.
- **AC:** AC-012.1 тіло `{ "query": "x", "mode": "keyword" }` приймається (200 або 409 за FR-018), зокрема з заголовком `Content-Type`, відмінним від `application/json`; AC-012.2 режими, відмінні від `keyword` і `expanded`, відхиляються (FR-016); AC-012.3 [OQ-02] `mode: "keyword"` не надсилає запитів до Ollama; `mode: "expanded"` надсилає рівно один запит до `/api/generate`.
- **Перевірка:** T.

### FR-013. Пошук документів за ключовими словами
- **Опис:** Система знаходить документи, що містять хоча б один терм запиту, використовуючи активний інвертований індекс.
- **Обґрунтування:** Основна функція пошуку.
- **Джерело:** SRC-A §Мета («пошук за ключовими словами (інвертований індекс)»), п.4. Семантика OR і нормалізація — P (OQ-03, OQ-21).
- **Пріоритет / Походження:** Must / M (семантика — P).
- **Передумови:** Існує активний індекс.
- **Тригер:** Валідний запит з `mode: "keyword"`.
- **Очікувана поведінка:** Запит нормалізується тими самими правилами, що й документи (OQ-21; пропозиція: нижній регістр, розбиття за не-буквено-цифровими символами). Результат — документи, що містять хоча б один терм (OR), не більше `SEARCH_TOP_K` (конфігурація, OQ-06).
- **Постумови:** Індекс не змінюється.
- **Пов'язані:** FR-014, FR-015, FR-017, FR-020.
- **Залежності:** FR-003, FR-012.
- **AC:** AC-013.1 на тестовому корпусі за `SEARCH_TOP_K` ≥ 12 кожен очікуваний документ є в результатах (таблиця DEL-09); AC-013.2 жоден документ без термів запиту не повертається; AC-013.3 пошук нечутливий до регістру; AC-013.4 кількість результатів ≤ `SEARCH_TOP_K`.
- **Перевірка:** T.

### FR-014. Ранжування результатів
- **Опис:** Результати впорядковано за спаданням `score`.
- **Обґрунтування:** Приклад SRC-A містить `score`; без ранжування поле не має сенсу.
- **Джерело:** SRC-A §Специфікація REST API (`score`). Формула — P (OQ-04; пропозиція TF-IDF).
- **Пріоритет / Походження:** Must / M (формула — P).
- **Передумови:** FR-013.
- **Тригер:** Формування відповіді пошуку.
- **Очікувана поведінка:** `score` — невід'ємне число; документ з більшою релевантністю за обраною формулою має більший `score`; при рівних `score` порядок детермінований (пропозиція: за `doc_id` за зростанням).
- **Постумови:** —
- **Пов'язані:** FR-015.
- **Залежності:** FR-013.
- **AC:** AC-014.1 `score[i] ≥ score[i+1]` для всіх i; AC-014.2 на контрольному корпусі порядок збігається з еталонним розрахунком формули; AC-014.3 повторний запит повертає той самий порядок.
- **Перевірка:** T.

### FR-015. Формат відповіді пошуку
- **Опис:** Відповідь містить масив `results` (кожен елемент: `doc_id`, `score`, `snippet`) і `time_ms`.
- **Обґрунтування:** Фіксований контракт SRC-A.
- **Джерело:** SRC-A §Специфікація REST API. Визначення snippet — P (OQ-05).
- **Пріоритет / Походження:** Must / M.
- **Передумови:** FR-013.
- **Тригер:** Завершення пошуку.
- **Очікувана поведінка:** `doc_id` — рядок (OQ-18); `score` — число; `snippet` — фрагмент тексту документа, що містить хоча б одне входження терма **пошукової множини**, довжиною не більше `SNIPPET_MAX_CHARS` (конфігурація, OQ-05). Пошукова множина: для REST — терми запиту (за пропозицією OQ-02); для WS — терми запиту ∪ `expanded_terms` (FR-020); `time_ms` — ціле, час виконання пошуку.
- **Постумови:** —
- **Пов'язані:** FR-014, FR-024.
- **Залежності:** FR-013.
- **AC:** AC-015.1 структура і типи збігаються з `openapi.yaml#/components/schemas/SearchResponse`; AC-015.2 `snippet` кожного результату містить (без урахування регістру) хоча б один терм пошукової множини; у WS для документа, знайденого лише за розширеним термом, snippet містить цей розширений терм; AC-015.3 довжина `snippet` ≤ `SNIPPET_MAX_CHARS`; AC-015.4 інших полів немає.
- **Перевірка:** T.

### FR-016. Валідація пошукового запиту
- **Опис:** Некоректний пошуковий запит відхиляється.
- **Обґрунтування:** Явна обробка помилок вводу.
- **Джерело:** P (OQ-11).
- **Пріоритет / Походження:** Must / P (необхідна для Must NFR-009, правило `01` §1.9).
- **Передумови:** —
- **Тригер:** `POST /api/search` з невалідним тілом.
- **Очікувана поведінка:** 400 з форматом помилки, якщо: тіло не є валідним JSON-об'єктом; `query` відсутній, не рядок, порожній або складається лише з пробілів; `query` довший за `MAX_QUERY_LENGTH` (конфігурація, OQ-06); `mode` відсутній або не рядок; `mode` ≠ `"keyword"` (код помилки `unsupported_mode`). Пропозиція: `mode` обов'язковий (OQ-11).
- **Постумови:** —
- **Пов'язані:** FR-012, FR-031.
- **Залежності:** FR-012.
- **AC:** AC-016.1 кожен випадок зі списку → 400 і відповідний код помилки (06 §2.4).
- **Перевірка:** T.

### FR-017. Порожній результат пошуку
- **Опис:** Якщо жоден документ не відповідає запиту, повертається порожній масив результатів.
- **Обґрунтування:** Відсутність результату не є помилкою.
- **Джерело:** P (випливає з контракту SRC-A).
- **Пріоритет / Походження:** Must / P.
- **Передумови:** Активний індекс.
- **Тригер:** Запит без збігів.
- **Очікувана поведінка:** 200, `results: []`, `time_ms` присутній.
- **Постумови:** —
- **Пов'язані:** FR-013, FR-029.
- **Залежності:** FR-013.
- **AC:** AC-017.1 запит з неіснуючим термом → 200 і порожній масив.
- **Перевірка:** T.

### FR-018. Пошук до побудови індексу
- **Опис:** Пошук до першої успішної побудови повертає помилку «індекс не готовий».
- **Обґрунтування:** Поведінка не визначена в SRC-A; порожній результат приховав би помилку оператора.
- **Джерело:** P (OQ-09).
- **Пріоритет / Походження:** Should / P.
- **Передумови:** Активного індексу немає.
- **Тригер:** `POST /api/search` або запит через WebSocket.
- **Очікувана поведінка:** REST: 409 з кодом `index_not_ready`. WebSocket: стан індексу перевіряється до виклику Ollama; сервер надсилає лише подію `error` з тим самим кодом (FR-027) — без `query_expansion` і `keyword_search`.
- **Постумови:** —
- **Пов'язані:** FR-011, FR-027.
- **Залежності:** FR-012, FR-027.
- **AC:** AC-018.1 REST → 409 `index_not_ready`; AC-018.2 WS → єдина подія `error` з кодом `index_not_ready`, без `query_expansion`; з'єднання відкрите; до Ollama запит не надсилається.
- **Перевірка:** T.

### FR-035. Пошук під час повторної побудови
- **Опис:** Під час побудови нового індексу пошук обслуговується попереднім активним індексом.
- **Обґрунтування:** Сервер не має блокувати клієнтів на час побудови (паралельна обробка запитів).
- **Джерело:** SRC-A §Мета (паралельна обробка запитів); семантика — P (OQ-10).
- **Пріоритет / Походження:** Should / P.
- **Передумови:** Існує активний індекс; триває нова побудова.
- **Тригер:** Пошуковий запит.
- **Очікувана поведінка:** Відповідь базується на попередньому індексі до моменту атомарної активації нового (FR-008). Якщо активного індексу ще немає — FR-018.
- **Постумови:** —
- **Пов'язані:** FR-008, FR-028, NFR-004.
- **Залежності:** FR-008.
- **AC:** AC-035.1 пошуки, запущені під час побудови, завершуються 200 з результатами, ідентичними результатам попереднього індексу; AC-035.2 жоден пошук не повертає частково побудований індекс.
- **Перевірка:** T.

## Група QEX. Розширення запиту (LLM)

### FR-019. Розширення запиту через Ollama
- **Опис:** Система отримує від Ollama ключові слова та синоніми для запиту через `/api/generate`.
- **Обґрунтування:** Критерій «Query expansion (LLM)».
- **Джерело:** SRC-A §Основні вимоги п.5; SRC-SYL §Критерії.
- **Пріоритет / Походження:** Must / M (постобробка — P).
- **Передумови:** Ollama доступна з налаштованою моделлю (OQ-13).
- **Тригер:** Запит через WebSocket (FR-022) або REST з `mode: "expanded"` (FR-012).
- **Очікувана поведінка:** Сервер надсилає запит на `/api/generate` Ollama (M) і перетворює відповідь на список `expanded_terms` (M). Правила постобробки — P (OQ-14, OQ-21): терми нормалізовано правилами токенізації, без дублікатів, без термів початкового запиту, не більше `MAX_EXPANDED_TERMS` (конфігурація).
- **Постумови:** —
- **Пов'язані:** FR-012, FR-020, FR-021, FR-023.
- **Залежності:** CON-008.
- **AC:** AC-019.1 [P] за контрольованої відповіді Ollama зі словами `a, b, B, query` для запиту `query` результат `["a","b"]`; AC-019.2 на реальній Ollama для запиту з тестової таблиці `expanded_terms` непорожній; AC-019.3 [P] кількість ≤ `MAX_EXPANDED_TERMS`; AC-019.4 запит до Ollama йде на шлях `/api/generate`.
- **Перевірка:** T.

### FR-020. Використання розширених термінів у пошуку
- **Опис:** Етап `keyword_search` пайплайну шукає за об'єднанням початкових і розширених термінів.
- **Обґрунтування:** Пайплайн SRC-A: «query expansion → пошук за ключовими словами».
- **Джерело:** SRC-A §Мета.
- **Пріоритет / Походження:** Must / M. Вага розширених термінів — P (OQ-04).
- **Передумови:** FR-019 завершився (успішно або fallback).
- **Тригер:** Перехід пайплайну до `keyword_search`.
- **Очікувана поведінка:** Набір пошукових термів = терми початкового запиту ∪ `expanded_terms`. Документ, що містить лише розширений терм, може потрапити в результати.
- **Постумови:** —
- **Пов'язані:** FR-013, FR-024.
- **Залежності:** FR-013, FR-019.
- **AC:** AC-020.1 якщо контрольована Ollama повертає терм `t`, якого немає в запиті, документ лише з `t` є в результатах `keyword_search`.
- **Перевірка:** T.

### FR-021. Fallback за недоступності Ollama
- **Опис:** Якщо розширення не вдалося (недоступність, тайм-аут, некоректна відповідь), пайплайн продовжується з початковим запитом.
- **Обґрунтування:** Збій зовнішнього сервісу не має ламати пошук (NFR-008).
- **Джерело:** P (OQ-14).
- **Пріоритет / Походження:** Must / P.
- **Передумови:** Запит на розширення ініційовано.
- **Тригер:** Помилка з'єднання, тайм-аут (NFR-020) або відповідь, з якої не вдалося отримати жодного терма.
- **Очікувана поведінка:** `expanded_terms: []`; пошук виконується за початковими термами; збій логується. Пропозиція: дані етапу `query_expansion` додатково не змінюються (контракт SRC-A не має поля для причини збою, OQ-11).
- **Постумови:** —
- **Пов'язані:** FR-002, FR-023, NFR-008, NFR-020.
- **Залежності:** FR-019, NFR-020.
- **AC:** AC-021.1 Ollama зупинено → пайплайн надсилає `query_expansion` з `expanded_terms: []`, потім `keyword_search`, потім `done`; AC-021.2 Ollama не відповідає довше тайм-ауту → те саме, подія `query_expansion` надходить не пізніше `OLLAMA_TIMEOUT_MS` + `TIMING_TOLERANCE_MS` від запиту (NFR-020); AC-021.3 відповідь Ollama без придатних термів → те саме.
- **Перевірка:** T.

## Група WS. WebSocket-стрімінг

### FR-022. WebSocket-з'єднання і прийом запиту
- **Опис:** Система приймає WebSocket-з'єднання на `/ws/search` і повідомлення клієнта `{ "query": "..." }`.
- **Обґрунтування:** Критерій «WebSocket стрімінг».
- **Джерело:** SRC-A §Основні вимоги п.6; §WebSocket /ws/search; SRC-SYL §Критерії.
- **Пріоритет / Походження:** Must / M. Кілька запитів в одній сесії — P (OQ-12).
- **Передумови:** —
- **Тригер:** WebSocket handshake на `/ws/search`, далі текстове повідомлення.
- **Очікувана поведінка:** Після валідного повідомлення запускається пайплайн (FR-023…FR-026). Пропозиція (OQ-12): після `done` з'єднання залишається відкритим, і клієнт може надіслати наступний запит; у сесії одночасно виконується не більше одного пайплайну; повідомлення, надіслане під час виконання пайплайну, не ставиться в чергу, а відхиляється подією `error` `pipeline_busy` (FR-027).
- **Постумови:** —
- **Пов'язані:** FR-023…FR-027.
- **Залежності:** CON-006.
- **AC:** AC-022.1 handshake на `/ws/search` успішний; AC-022.2 валідний запит запускає пайплайн; AC-022.3 [P, OQ-12] другий запит після `done` у тій самій сесії дає повний пайплайн.
- **Перевірка:** T.

### FR-023. Подія `query_expansion`
- **Опис:** Перше повідомлення пайплайну — етап `query_expansion` з початковим запитом і розширеними термінами.
- **Джерело:** SRC-A §WebSocket (`{ "stage": "query_expansion", "data": {"original": "...", "expanded_terms": [...]} }`).
- **Обґрунтування:** Фіксований контракт.
- **Пріоритет / Походження:** Must / M.
- **Передумови:** FR-022.
- **Тригер:** Завершення FR-019 / FR-021.
- **Очікувана поведінка:** `stage` = `"query_expansion"`; `data.original` = значення `query` з повідомлення клієнта без змін; `data.expanded_terms` — масив рядків (може бути порожнім).
- **Постумови:** —
- **Пов'язані:** FR-019, FR-021.
- **Залежності:** FR-019.
- **AC:** AC-023.1 структура збігається з `06 §3.4 WS-E-01`; AC-023.2 `original` дорівнює надісланому `query`.
- **Перевірка:** T.

### FR-024. Подія `keyword_search`
- **Опис:** Друге повідомлення — етап `keyword_search` з результатами і часом пошуку.
- **Джерело:** SRC-A §WebSocket (`{ "stage": "keyword_search", "data": {"results": [...], "time_ms": 12} }`).
- **Обґрунтування:** Фіксований контракт.
- **Пріоритет / Походження:** Must / M. Структура елементів `results` — P: така сама, як у REST (OQ-11).
- **Передумови:** FR-023 надіслано.
- **Тригер:** Завершення пошуку FR-020.
- **Очікувана поведінка:** `data.results` — масив елементів `{doc_id, score, snippet}` (як FR-015), `data.time_ms` — ціле, час етапу пошуку.
- **Постумови:** —
- **Пов'язані:** FR-015, FR-020.
- **Залежності:** FR-020, FR-015.
- **AC:** AC-024.1 структура збігається з `06 §3.4 WS-E-02`; AC-024.2 результати впорядковано за FR-014.
- **Перевірка:** T.

### FR-025. Подія `done`
- **Опис:** Останнє повідомлення пайплайну — `{ "stage": "done" }`.
- **Джерело:** SRC-A §WebSocket.
- **Обґрунтування:** Фіксований контракт.
- **Пріоритет / Походження:** Must / M (форма без `data` — P, OQ-31).
- **Передумови:** FR-024 надіслано.
- **Тригер:** Завершення пайплайну.
- **Очікувана поведінка:** Повідомлення з `stage: "done"`. Наявність поля `data` — суперечність завдання C-07 (OQ-31, B). Діюча пропозиція: сервер надсилає рівно `{ "stage": "done" }`, як у прикладі SRC-A; клієнти системи (Web UI, тести) приймають `done` як з `data`, так і без нього.
- **Постумови:** Сесія готова до наступного запиту (OQ-12) або закривається.
- **Пов'язані:** FR-026.
- **Залежності:** FR-024.
- **AC:** AC-025.1 повідомлення з `stage: "done"` надходить після `keyword_search`; AC-025.2 [P, OQ-31] повідомлення не містить поля `data`.
- **Перевірка:** T.

### FR-026. Порядок і окремість подій
- **Опис:** Етапи пайплайну надсилаються як окремі повідомлення в порядку `query_expansion`, `keyword_search`, `done`, кожне — одразу після завершення етапу.
- **Обґрунтування:** SRC-A: «кожен етап передається клієнту як окреме повідомлення»; критерій «WebSocket стрімінг».
- **Джерело:** SRC-A §Основні вимоги п.6; SRC-SYL §Критерії.
- **Пріоритет / Походження:** Must / M.
- **Передумови:** FR-022.
- **Тригер:** Пайплайн.
- **Очікувана поведінка:** Рівно три повідомлення на запит у вказаному порядку; `query_expansion` надсилається до початку етапу пошуку, а не разом з ним.
- **Постумови:** —
- **Пов'язані:** FR-023…FR-025, FR-033.
- **Залежності:** FR-023, FR-024, FR-025.
- **AC:** AC-026.1 послідовність stage = [query_expansion, keyword_search, done]; AC-026.2 з контрольованою затримкою Ollama D мс подія `query_expansion` приходить клієнту не раніше D мс після запиту і раніше події `keyword_search` (окремими кадрами).
- **Перевірка:** T.

### FR-027. Помилки в WebSocket-сесії
- **Опис:** Некоректне повідомлення клієнта або неможливість виконати пайплайн дає подію помилки без закриття з'єднання.
- **Обґрунтування:** SRC-A не визначає помилок WS; без цього клієнт не відрізнить збій від очікування.
- **Джерело:** P (OQ-11). **Відхилення від SRC-A:** додається значення `stage: "error"`, якого немає в контракті (DEV-01).
- **Пріоритет / Походження:** Must / P (необхідна для Must NFR-009, правило `01` §1.9).
- **Передумови:** FR-022.
- **Тригер:** Повідомлення не є валідним JSON або не є JSON-об'єктом; бінарний кадр; немає `query`; `query` не рядок, порожній, складається лише з пробілів або довший за `MAX_QUERY_LENGTH`; індекс не готовий (FR-018); повідомлення надійшло, поки попередній пайплайн сесії ще виконується (OQ-12).
- **Очікувана поведінка:** Сервер надсилає `{ "stage": "error", "data": { "code": "...", "message": "..." } }`; з'єднання залишається відкритим; інші сесії не зачеплено.
- **Постумови:** Сесія готова до наступного запиту.
- **Пов'язані:** FR-016, FR-018.
- **Залежності:** FR-022.
- **AC:** AC-027.1 кожен тригер → подія `error` з відповідним кодом (06 §3.5); AC-027.2 після події `error` валідний запит у тій самій сесії дає повний пайплайн.
- **Перевірка:** T.

## Група CON. Одночасна обробка клієнтів

### FR-028. Одночасна обробка запитів кількох клієнтів
- **Опис:** Сервер обробляє запити кількох клієнтів (REST і WebSocket) одночасно; обробка одного запиту не чекає завершення іншого незалежного запиту.
- **Обґрунтування:** SRC-A: «обробляти запити від кількох клієнтів одночасно»; графік throughput vs клієнти.
- **Джерело:** SRC-A §Завдання, §Мета; записка розд. 4; SRC-B п.24.
- **Пріоритет / Походження:** Must / M.
- **Передумови:** —
- **Тригер:** Кілька одночасних запитів.
- **Очікувана поведінка:** Запити обробляються паралельно; кожен клієнт отримує лише власні відповіді й події; результати збігаються з результатами тих самих запитів, виконаних послідовно.
- **Постумови:** —
- **Пов'язані:** FR-035, NFR-003, NFR-004, NFR-007.
- **Залежності:** FR-013, FR-022.
- **AC:** AC-028.1 K одночасних клієнтів (K з набору бенчмарку, OQ-17) → усі відповіді 200 і збігаються з послідовними; AC-028.2 K одночасних WS-сесій отримують лише свої події (`original` = свій запит); AC-028.3 K одночасних WS-сесій при затримці контрольованої Ollama D мс на кожен виклик отримують `done` за загальний час < K·D (доказ паралельності; затримка створюється лише двійником FIX-04, без тестових хуків у сервері).
- **Перевірка:** T.

### FR-030. Обробка помилок CLI
- **Опис:** Консольний клієнт повідомляє про помилки і завершується з ненульовим кодом.

- **Залежності:** FR-029.

## Група TPL. Власний пул потоків (компонентні вимоги)

Пул — внутрішній компонент, тому його поведінка не спостерігається через REST/WS напряму. Ці вимоги перевіряються модульними тестами (`09` §2) і є обов'язковими, бо пул — предмет критерію «Thread pool» (SRC-SYL) і `.claude/rules/architecture.md` §6. Деталі, яких немає в завданні, позначено P з посиланням на OQ-32.

### FR-036. Створення пулу із заданою кількістю потоків
- **Опис:** Пул створюється із заданою кількістю робочих потоків `p ≥ 1`; потоки існують до завершення роботи пулу (FR-040).
- **Обґрунтування:** Керована кількість потоків — основа FR-004 і бенчмарку.
- **Джерело:** SRC-A §Основні вимоги п.3 («самостійно реалізованого пулу потоків»; «варіювання кількості потоків»); життєвий цикл «пул на одну побудову» — P (OQ-32).
- **Пріоритет / Походження:** Must / M (життєвий цикл — P).
- **Передумови:** —
- **Тригер:** Створення пулу (пропозиція OQ-32: на початку кожної побудови з `p = threads`).
- **Очікувана поведінка:** Після створення існує рівно `p` робочих потоків, що чекають на задачі без активного очікування (busy waiting); `p < 1` відхиляється помилкою створення.
- **Постумови:** Пул готовий приймати задачі.
- **Пов'язані:** FR-004, FR-006.
- **Залежності:** CON-003.
- **AC:** AC-036.1 після створення з `p` кількість робочих потоків = `p`; AC-036.2 у простої пул не споживає CPU понад фоновий рівень (перевірка: час CPU процесу за 1 с простою < 5 % одного ядра, P); AC-036.3 `p = 0` → помилка створення.
- **Перевірка:** T.

### FR-037. Подання задачі
- **Опис:** Пул приймає задачу (виконуваний об'єкт) і виконує її рівно один раз в одному з робочих потоків.
- **Обґрунтування:** Базова операція пулу; NFR-006 «рівно один раз».
- **Джерело:** SRC-A §Основні вимоги п.3; поведінка черги — P (OQ-32).
- **Пріоритет / Походження:** Must / M (черга — P).
- **Передумови:** Пул не завершується (FR-040).
- **Тригер:** Виклик подання задачі.
- **Очікувана поведінка:** Задача потрапляє в чергу пулу і виконується вільним робочим потоком. Одночасно виконується не більше `p` задач. Подання з кількох потоків одночасно безпечне. [AD-10] Черга — власна структура поверх масиву або списку (поширення CON-015 на чергу не затверджене). Пропозиція (OQ-32): черга обмежена місткістю `POOL_QUEUE_CAPACITY`; якщо вона заповнена, подання блокує потік, що подає, до звільнення місця.
- **Постумови:** Задачу виконано або вона в черзі.
- **Пов'язані:** FR-006, NFR-006, CON-015 (P, OQ-37).
- **Залежності:** FR-036.
- **AC:** AC-037.1 N = 10 000 задач, поданих з 4 потоків, виконано рівно N разів (лічильник за ID задачі, без пропусків і дублів); AC-037.2 одночасно активних задач ≤ `p` і = `p` хоча б раз при N ≥ p; AC-037.3 [P] при заповненій черзі подання чекає, а не губить задачу.
- **Перевірка:** T (+TSan).

### FR-038. Очікування завершення задач
- **Опис:** Ініціатор може дочекатися завершення конкретної задачі або групи поданих ним задач.
- **Обґрунтування:** Без надійного виявлення завершення побудова не знає, коли активувати індекс (`.claude/rules/architecture.md` §8 «Completion synchronization»).
- **Джерело:** P (OQ-32); підтримує FR-006.
- **Пріоритет / Походження:** Must / P.
- **Передумови:** Задачі подано.
- **Тригер:** Виклик очікування.
- **Очікувана поведінка:** Очікування повертається лише після завершення (успішного чи аварійного) усіх задач, яких воно стосується, без активного очікування.
- **Постумови:** Результати задач видимі потоку-ініціатору (happens-before).
- **Пов'язані:** FR-006, FR-039.
- **Залежності:** FR-037.
- **AC:** AC-038.1 після очікування групи з N задач, кожна з яких записує свій результат, ініціатор бачить усі N результатів (TSan без звітів); AC-038.2 очікування не повертається раніше завершення найповільнішої задачі (задача із затримкою 200 мс).
- **Перевірка:** T (+TSan).

### FR-039. Обробка винятків у задачі
- **Опис:** Виняток, що вилетів із задачі, перехоплюється пулом і передається ініціатору; робочий потік продовжує працювати.
- **Обґрунтування:** Виняток, що вийшов із потоку, завершує процес C++ (`std::terminate`); `.claude/rules/code-quality.md` §5.
- **Джерело:** P (OQ-32); `.claude/rules/architecture.md` §6.
- **Пріоритет / Походження:** Must / P.
- **Передумови:** —
- **Тригер:** Задача кидає виняток.
- **Очікувана поведінка:** Виняток зберігається в результаті задачі і повторно кидається (або повертається як помилка) під час очікування (FR-038). Кількість робочих потоків не зменшується.
- **Постумови:** Пул працездатний.
- **Пов'язані:** FR-042.
- **Залежності:** FR-038.
- **AC:** AC-039.1 задача з винятком → ініціатор отримує той самий тип винятку; AC-039.2 після 100 задач із винятками пул виконує 100 звичайних задач з усіма `p` потоками.
- **Перевірка:** T (+TSan).

### FR-040. Завершення роботи пулу
- **Опис:** Пул коректно завершує роботу: припиняє приймати задачі, обробляє вже прийняті і приєднує (join) усі робочі потоки.
- **Обґрунтування:** Без коректного завершення — витоки потоків, дедлоки при виході (NFR-006, NFR-026).
- **Джерело:** P (OQ-32: «виконати прийняті» чи «відкинути невиконані»); `.claude/rules/architecture.md` §6.
- **Пріоритет / Походження:** Must / P.
- **Передумови:** —
- **Тригер:** Явний виклик завершення або знищення пулу.
- **Очікувана поведінка:** Пропозиція: усі задачі, прийняті до початку завершення, виконуються; потім усі потоки завершуються і приєднуються. Повторний виклик завершення безпечний (ідемпотентний). Знищення пулу без явного виклику виконує завершення.
- **Постумови:** Жодного робочого потоку пулу не існує.
- **Пов'язані:** FR-041, NFR-006, NFR-026.
- **Залежності:** FR-036.
- **AC:** AC-040.1 завершення з 1000 задачами в черзі виконує всі 1000 і повертається; AC-040.2 після завершення кількість потоків пулу = 0; AC-040.3 подвійне завершення не дає помилки і не зависає; AC-040.4 100 циклів створення/завершення без зависань (тайм-аут тесту 30 с, P).
- **Перевірка:** T (+TSan).

### FR-041. Подання задачі після завершення
- **Опис:** Подання задачі в пул, що завершується або завершився, відхиляється явною помилкою.
- **Обґрунтування:** Інакше задача мовчки губиться (`.claude/rules/architecture.md` §6 «Can tasks be submitted after shutdown?»).
- **Джерело:** P (OQ-32).
- **Пріоритет / Походження:** Must / P.
- **Передумови:** Розпочато FR-040.
- **Тригер:** Подання задачі.
- **Очікувана поведінка:** Подання завершується помилкою; задача не виконується. Подання, заблоковане на заповненій черзі (FR-037) на момент початку завершення, пробуджується і завершується тією самою помилкою.
- **Постумови:** —
- **Пов'язані:** FR-040.
- **Залежності:** FR-040.
- **AC:** AC-041.1 подання після завершення → помилка, задача не виконана (лічильник = 0); AC-041.2 [P, OQ-32] потік, заблокований на повній черзі, після початку завершення отримує помилку не пізніше ніж за 1 с (без зависання).
- **Перевірка:** T.

## Група IDX (доповнення)

### FR-042. Аварійне завершення задачі індексації
- **Опис:** Якщо задача індексації завершилася винятком, що не є помилкою читання за класифікацією FR-003 (наприклад, нестача пам'яті або порушення внутрішнього інваріанта), уся побудова вважається невдалою.
- **Обґрунтування:** Частково побудований індекс порушив би NFR-005; усуває суперечність між FR-006 і UC-03 E4 (AUD-1-08).
- **Джерело:** P (OQ-19).
- **Пріоритет / Походження:** Must / P.
- **Передумови:** Триває побудова.
- **Тригер:** Задача індексації кидає виняток (наприклад, нестача пам'яті або внутрішня помилка).
- **Очікувана поведінка:** Побудова дочікується завершення решти поданих задач (FR-038), не активує новий індекс і відповідає 500 `index_build_failed`. Попередній активний індекс і статистика не змінюються. Пул побудови завершується (FR-040), і наступна побудова можлива.
- **Постумови:** Стан індексу — як до запиту; прапорець «побудова триває» знято.
- **Пов'язані:** FR-006, FR-039, FR-008.
- **Залежності:** FR-039, FR-003.
- **AC:** AC-042.1 в інтеграційному тесті з двійником, внесеним через ін'єкцію залежності (без тестових режимів у виробничому бінарнику), одна задача кидає внутрішній виняток → відповідь 500 `index_build_failed`; AC-042.2 пошук після цього повертає результати попереднього індексу; AC-042.3 наступна побудова без збою → 200.
- **Перевірка:** T (інтеграційний тест з тестовим двійником).

## Група GEN. Загальні помилки HTTP

### FR-043. Обробка невідомих шляхів, методів і завеликих тіл
- **Опис:** Невідомий шлях, недозволений метод на відомому шляху і тіло понад `MAX_REQUEST_BODY_BYTES` дають помилку у форматі API, а не обрив з'єднання чи HTML-сторінку.
- **Обґрунтування:** Стабільна поведінка для клієнтів і перевіряльника; NFR-009.
- **Джерело:** P (OQ-27, DEV-03).
- **Пріоритет / Походження:** Should / P.
- **Передумови:** —
- **Тригер:** Відповідний HTTP-запит.
- **Очікувана поведінка:** Невідомий шлях → 404 `not_found`; відомий шлях з іншим методом → 405 `method_not_allowed`; тіло більше ліміту → 413 `payload_too_large`. Заголовок `Content-Type` не перевіряється (FR-004, FR-012).
- **Постумови:** Стан не змінюється.
- **Пов'язані:** NFR-009, NFR-013.
- **Залежності:** —
- **AC:** AC-043.1 `GET /api/unknown` → 404 `not_found`; AC-043.2 `DELETE /api/index` → 405 `method_not_allowed`; AC-043.3 тіло `MAX_REQUEST_BODY_BYTES + 1` байт на `/api/search` → 413 `payload_too_large`.
- **Перевірка:** T.
