# 03. Нефункціональні вимоги

Правило числових цілей: SRC-A та SRC-SYL не задають жодних числових порогів продуктивності.

Позначення кількості процесорів: **L** — кількість логічних процесорів машини бенчмарку (з урахуванням лімітів контейнера), **C** — кількість фізичних ядер. Набір вимірюваних p базується на L; умова зменшення часу (NFR-001) — на C, бо понад C апаратні потоки ділять ядра і прискорення може зникати. Тестові допуски часу задаються параметром `TIMING_TOLERANCE_MS` (`09` §1; пропозиція 500 мс). Тому кожне число нижче або є параметром конфігурації, або позначене як **запропонована ціль (P)** з посиланням на відкрите питання. Жодне таке число не є затвердженою вимогою, доки власник не прийме рішення.

Поля: **Категорія**, **Опис**, **Обґрунтування**, **Джерело**, **Пріоритет / Походження**, **Вимірювані критерії прийняття**, **Перевірка**, **Залежності**.

## Продуктивність і масштабованість

### NFR-001. Зменшення часу побудови зі зростанням кількості потоків
- **Категорія:** Performance / Scalability.
- **Опис:** Час побудови індексу на бенчмарковому датасеті зменшується при збільшенні `threads` від 1 до C.
- **Обґрунтування:** Прямий критерій «Thread pool»: «час побудови зменшується при збільшенні кількості потоків».
- **Джерело:** SRC-SYL §Критерії («Thread pool»).
- **Пріоритет / Походження:** Must / M (межі p і поріг — P, OQ-25).
- **Критерії (P, OQ-25):** на тому самому датасеті й машині: якщо C ≥ 2 — медіана `T(2)` < медіана `T(1)`; якщо C ≥ 4 — додатково медіана `T(C)` < медіана `T(2)`. Якщо C < 2, критерій продемонструвати неможливо; бенчмарк запускається на іншій машині (ASM-1). Числовий мінімум прискорення не встановлюється (не задано в SRC).
- **Перевірка:** A — TEST-PERF-01.
- **Залежності:** FR-004, FR-006, NFR-014, NFR-023.

### NFR-002. Звіт про прискорення та ефективність
- **Категорія:** Scalability.
- **Опис:** Для кожного виміряного p звітуються `T(p)`, `S(p) = T(1)/T(p)`, `E(p) = S(p)/p` і графік «час vs потоки» для p від 1 до N.
- **Обґрунтування:** SRC-A записка розд. 4; SRC-B п.20 (прискорення).
- **Джерело:** SRC-A §Основні вимоги п.8 («від 1 до N»), §Вимоги до записки розд. 4.
- **Пріоритет / Походження:** Must / M. Значення N — P (OQ-17; пропозиція: N ≥ кількість логічних процесорів).
- **Критерії:** Набір p (P, OQ-17): 1, 2, 4, 8, … (степені двійки, менші за L), а також C і L, якщо вони не степені двійки, і щонайменше одне значення понад L (для показу насичення). Таблиця і графік містять кожне p з набору; S(1) = 1; кожна точка — медіана R повторів (R — OQ-17) з розкидом (min/max).
- **Перевірка:** A, I — TEST-PERF-01.
- **Залежності:** NFR-001, NFR-023.

### NFR-003. Вимірювання throughput за кількістю одночасних клієнтів
- **Категорія:** Scalability / Concurrency.
- **Опис:** Вимірюється throughput (успішні запити / час) і затримка (медіана, p95) для набору кількостей одночасних клієнтів; будується графік throughput vs клієнти.
- **Обґрунтування:** SRC-A записка розд. 4; SRC-SYL §Критерії «Дослідження масштабованості».
- **Джерело:** SRC-A §Вимоги до записки розд. 4; SRC-SYL §Критерії.
- **Пріоритет / Походження:** Must / M. Ендпоінт навантаження, кількості клієнтів, тривалість — P (OQ-17; пропозиція: `POST /api/search` keyword, клієнти {1, 2, 4, 8, 16, 32}).
- **Критерії:** Для кожної кількості клієнтів зафіксовано: всього запитів, успішних, неуспішних, тривалість, throughput, медіана і p95 затримки. Частка неуспішних запитів = 0 (P).
- **Перевірка:** A — TEST-PERF-02.
- **Залежності:** FR-028, NFR-023.

### NFR-022. Облік споживання пам'яті
- **Категорія:** Resource utilization.
- **Опис:** Під час бенчмарку побудови фіксується пікове споживання пам'яті процесом сервера.
- **Обґрунтування:** ASM-3: індекс датасету обсягом ≥ поріг C-01 у пам'яті; аналіз вузьких місць (DEL-10).
- **Джерело:** P (підтримує DEL-10).
- **Пріоритет / Походження:** Could / P.
- **Критерії:** Таблиця бенчмарку містить пікову пам'ять (RSS) для кожного p.
- **Перевірка:** A — TEST-PERF-01.
- **Залежності:** NFR-002.

### NFR-023. Відтворюваність вимірювань
- **Категорія:** Performance (методика).
- **Опис:** Кожен бенчмарк запускається одним скриптом з фіксованими параметрами і фіксує умови вимірювання.
- **Обґрунтування:** Висновки про продуктивність мають бути відтворювані (CLAUDE.md §12); без цього графіки CC-11 не можна захистити.
- **Джерело:** P; необхідна для NFR-001, NFR-002, NFR-003 (CC-11).
- **Пріоритет / Походження:** Must / P.
- **Критерії:** Звіт бенчмарку містить: модель CPU, кількість ядер/потоків, RAM, ОС, версію компілятора і прапорці, конфігурацію Docker (ліміти CPU/RAM), обсяг і кількість документів датасету, модель Ollama, хеш коміту, кількість повторів і прогрівів. Повторний запуск скрипту на тій самій машині дає медіани в межах розкиду попереднього запуску (P).
- **Перевірка:** I, A — TEST-PERF-01, TEST-PERF-02.
- **Залежності:** NFR-014.

## Конкурентність

### NFR-004. Відсутність станів гонки
- **Категорія:** Concurrency.
- **Опис:** Паралельна побудова індексу, паралельні пошуки та пошуки під час побудови не містять гонок даних.
- **Обґрунтування:** Критерій «Паралельна структура даних»: «відсутність станів гонки».
- **Джерело:** SRC-SYL §Критерії; SRC-A §Основні вимоги п.3; SRC-B п.7, п.9.
- **Пріоритет / Походження:** Must / M.
- **Критерії:** ThreadSanitizer не повідомляє жодної гонки на тестах TEST-CONC-01, TEST-CONC-02, TEST-CONC-03, TEST-UT-07…TEST-UT-09, TEST-UT-15, TEST-UT-16. Обмеження методу зафіксовано в `09-verification-strategy.md` §6.
- **Перевірка:** T.
- **Залежності:** CON-003, CON-004.

### NFR-005. Еквівалентність паралельного і послідовного індексу
- **Категорія:** Concurrency / Reliability.
- **Опис:** Індекс, побудований з будь-якою кількістю потоків, логічно ідентичний індексу, побудованому з 1 потоком на тих самих даних.
- **Обґрунтування:** Доказ коректності паралельної побудови (`.claude/rules/testing.md` §4).
- **Джерело:** P; підтримує SRC-SYL §Критерії («Паралельна структура даних»).
- **Пріоритет / Походження:** Must / P.
- **Критерії:** Для p ∈ {1, 2, 3, 4, 8, логічні CPU} на тестовому корпусі: однакова кількість документів, однаковий набір термів, однакові постинги (документ, частота) для кожного терма.
- **Перевірка:** T — TEST-IT-01.
- **Залежності:** FR-006.

### NFR-006. Відсутність взаємних блокувань і втрачених задач
- **Категорія:** Concurrency / Reliability.
- **Опис:** Кожна побудова завершується; кожна подана в пул задача виконується рівно один раз; завершення пулу не зависає.
- **Обґрунтування:** SRC-B п.8, п.9, п.25; якість власного пулу.
- **Джерело:** P; підтримує SRC-A §Основні вимоги п.3.
- **Пріоритет / Походження:** Must / P.
- **Критерії:** Стрес-тест: ≥ 100 послідовних побудов з випадковими p ∈ [1, min(2·L, `MAX_INDEX_THREADS`)] на тестовому корпусі завершуються, кожна в межах тайм-ауту тесту (P: 30 с на побудову малого корпусу); лічильник виконаних задач = кількості поданих.
- **Перевірка:** T — TEST-CONC-05, TEST-UT-07, TEST-UT-09.
- **Залежності:** CON-003.

### NFR-007. Ізоляція повільних запитів
- **Категорія:** Concurrency / Availability.
- **Опис:** Довге очікування відповіді Ollama в одній сесії не блокує обробку запитів інших клієнтів.
- **Обґрунтування:** SRC-A §Мета (паралельна обробка запитів).
- **Джерело:** SRC-A §Мета; P (критерій).
- **Пріоритет / Походження:** Should / P.
- **Критерії (P):** поки WS-сесія чекає на контрольовану Ollama із затримкою D = 5 с, `POST /api/search` іншого клієнта завершується менш ніж за D/2 = 2.5 с.
- **Перевірка:** T — TEST-RES-01.
- **Залежності:** FR-028.

## Надійність і доступність

### NFR-008. Стійкість до збою Ollama
- **Категорія:** Reliability.
- **Опис:** Недоступність, тайм-аут або некоректна відповідь Ollama не призводять до збою сервера чи пошуку.
- **Обґрунтування:** Зовнішня залежність; `.claude/rules/architecture.md` §9.
- **Джерело:** P.
- **Пріоритет / Походження:** Must / P.
- **Критерії:** За зупиненої Ollama: health → 200, `ollama: false`; REST-пошук → 200; WS-пайплайн → три етапи з `expanded_terms: []`; процес сервера продовжує працювати.
- **Перевірка:** T — TEST-API-02, TEST-IT-03, TEST-WS-02.
- **Залежності:** FR-021.

### NFR-009. Стійкість до помилок рівня запиту
- **Категорія:** Reliability.
- **Опис:** Некоректний запит, обрив з'єднання клієнта чи помилка обробки одного запиту не завершують процес сервера і не впливають на інші запити.
- **Обґрунтування:** `.claude/rules/code-quality.md` §5. Обов'язкова через автоматичну перевірку CC-03 і CC-07: перевіряльник може надсилати некоректні запити, і падіння сервера провалює всі наступні перевірки.
- **Джерело:** P (необхідна для CC-03, CC-07, CC-01).
- **Пріоритет / Походження:** Must / P.
- **Критерії:** Після серії некоректних запитів (TEST-RES-02) і обривів WS (TEST-WS-04) health → 200, валідний пошук → 200.
- **Перевірка:** T.
- **Залежності:** FR-016, FR-027.

### NFR-010. Доступність health під час побудови
- **Категорія:** Availability.
- **Опис:** `GET /api/health` відповідає під час побудови індексу.
- **Обґрунтування:** Перевіряльник може запитувати health у будь-який момент; побудова не повинна займати всі потоки обробки HTTP.
- **Джерело:** P.
- **Пріоритет / Походження:** Should / P.
- **Критерії (P):** під час побудови бенчмаркового датасету з p = L health повертає 200 за час ≤ `HEALTH_CHECK_TIMEOUT_MS` + `TIMING_TOLERANCE_MS`.
- **Перевірка:** T — TEST-API-13.
- **Залежності:** FR-001, FR-009.

### NFR-020. Обмежений тайм-аут виклику Ollama
- **Категорія:** Reliability.
- **Опис:** Кожен виклик Ollama має тайм-аут з конфігурації; після нього застосовується fallback.
- **Обґрунтування:** Без тайм-ауту пайплайн може зависнути.
- **Джерело:** P (значення — OQ-14).
- **Пріоритет / Походження:** Must / P.
- **Критерії:** Ollama, що не відповідає, → етап `query_expansion` надсилається не пізніше `OLLAMA_TIMEOUT_MS` + `TIMING_TOLERANCE_MS`.
- **Перевірка:** T — TEST-IT-03.
- **Залежності:** NFR-019.

## Переносимість і сумісність

### NFR-011. Запуск однією командою
- **Категорія:** Portability.
- **Опис:** На чистій машині з Docker та Docker Compose система запускається командою `docker compose up` з кореня репозиторію. Єдиний дозволений ручний крок до запуску — розміщення датасету в каталозі, вказаному в README (запропоноване відхилення DEV-04, бо датасет ≥ 1–2 ГБ не зберігається в Git). Модель Ollama не вимагає ручних дій (NFR-024).
- **Обґрунтування:** Критерій «Docker Compose».
- **Джерело:** SRC-A §Основні вимоги п.2; SRC-SYL §Критерії, §Перша атестація.
- **Пріоритет / Походження:** Must / M.
- **Критерії:** Зі свіжого клону з розміщеним датасетом `docker compose up` → протягом `READINESS_TIMEOUT_S` (параметр тесту, OQ-13) `GET /api/health` повертає 200; інших ручних дій не виконувалося.
- **Перевірка:** T — TEST-E2E-01.
- **Залежності:** NFR-012, FR-001.

### NFR-012. Склад сервісів Docker Compose
- **Категорія:** Compatibility / Deployability.
- **Опис:** `docker-compose.yml` містить сервіс пошукового сервера, сервіс Ollama і веб-контейнер Web UI (AD-07).
- **Обґрунтування:** Прямо вимагається.
- **Джерело:** SRC-A §Основні вимоги п.2.
- **Пріоритет / Походження:** Must / M.
- **Критерії:** `docker compose config --services` містить сервіс сервера, сервіс Ollama і веб-контейнер (AD-07); інших сервісів немає.
- **Перевірка:** I, T — TEST-E2E-01.
- **Залежності:** CON-007.

### NFR-013. Точна відповідність контрактам API
- **Категорія:** Compatibility.
- **Опис:** Елементи контракту SRC-A (шляхи, методи, назви і типи полів запитів і успішних відповідей REST, шлях WebSocket, значення `stage` для трьох етапів і структура їхніх `data`) не змінюються. Успішні відповіді не містять полів поза контрактом. Доповнення до контракту допускаються лише як затверджені відхилення DEV-01…DEV-04 (`12` §3).
- **Обґрунтування:** Автоматична перевірка критеріїв очікує заданий формат.
- **Джерело:** SRC-A §Основні вимоги п.4 («фіксований контракт»), §Специфікація REST API, §WebSocket.
- **Пріоритет / Походження:** Must / M.
- **Критерії:** Контрактні тести (TEST-API-*, TEST-WS-01) валідують відповіді за `openapi.yaml` з `additionalProperties: false`.
- **Перевірка:** T.
- **Залежності:** CON-005, CON-006.

### NFR-014. Вимоги до датасету
- **Категорія:** Compatibility (дані).
- **Опис:** Бенчмарковий датасет — текстові документи англійською мовою, загальний обсяг не менше порогу (див. суперечність C-01) і не менше 10 000 документів.
- **Обґрунтування:** Масштабованість має вимірюватися на реалістичному обсязі.
- **Джерело:** SRC-A §Вхідні текстові дані. **Суперечність C-01:** «не менше 2 ГБ» і «не менше 1 ГБ» в одному розділі (OQ-01).
- **Пріоритет / Походження:** Must / M.
- **Критерії:** Скрипт перевірки датасету звітує: кількість документів ≥ 10 000; сумарний обсяг ≥ поріг з OQ-01; усі файли — UTF-8 текст.
- **Перевірка:** T — TEST-DOC-05.
- **Залежності:** —

## Супроводжуваність

### NFR-015. Єдиний стиль коду
- **Категорія:** Maintainability.
- **Опис:** Весь код бекенду відформатовано в одному стилі, перевірка автоматизована. Вибір стилю (пропозиція: Google C++ Style, Допоміжна література 7) і форматера (пропозиція: `clang-format`) — P (OQ-33).
- **Обґрунтування:** Критерій «Інструкція та чистий код»; Допоміжна література 7.
- **Джерело:** SRC-SYL §Критерії («форматування коду в одному стилі»); SRC-A §Основні пункти п.13.
- **Пріоритет / Походження:** Must / M (стиль і інструмент — P, OQ-33).
- **Критерії:** Перевірка форматування обраним інструментом (P: `clang-format --dry-run --Werror`) на всіх файлах C++ завершується з кодом 0. Клієнти відформатовано інструментом їхньої мови (OQ-16).
- **Перевірка:** T — TEST-DOC-02.
- **Залежності:** —

### NFR-016. Збирання без попереджень і статичний аналіз
- **Категорія:** Maintainability.
- **Опис:** Бекенд збирається без попереджень компілятора з увімкненими попередженнями; статичний аналіз не має невирішених зауважень.
- **Обґрунтування:** «Чистота та якість програмного коду» (SRC-A п.8).
- **Джерело:** SRC-A §Основні вимоги п.8; P (конкретні прапорці).
- **Пріоритет / Походження:** Should / P.
- **Критерії:** Збирання з `-Wall -Wextra -Wpedantic -Werror` (P) успішне; `clang-tidy` (P) без зауважень або з задокументованими винятками.
- **Перевірка:** T — TEST-DOC-06.
- **Залежності:** —

### NFR-017. Історія Git за Conventional Commits
- **Категорія:** Maintainability.
- **Опис:** Репозиторій на GitHub має осмислену історію атомарних комітів у форматі Conventional Commits.
- **Обґрунтування:** Без Git робота не зараховується; критерій «Інструкція та чистий код»; захист.
- **Джерело:** SRC-SYL §Git; SRC-A §Основні вимоги п.8; SRC-SYL §Критерії захисту («коректно описані коміти»).
- **Пріоритет / Походження:** Must / M. Мінімальна кількість комітів не визначена (OQ-28).
- **Критерії:** Усі коміти, крім merge, відповідають шаблону `type(scope)?: description` з типами з `.claude/rules/git.md` §4; жоден коміт не змішує незалежні зміни (I); історія показує поступовий розвиток від першого коміту.
- **Перевірка:** T (скрипт перевірки повідомлень), I — TEST-DOC-03.
- **Залежності:** CON-010.

### NFR-019. Конфігурованість експлуатаційних параметрів
- **Категорія:** Maintainability / Portability.
- **Опис:** Порт сервера, URL Ollama, назва моделі, шлях до датасету, `threads` за замовчуванням, `MAX_INDEX_THREADS`, `SEARCH_TOP_K`, `SNIPPET_MAX_CHARS`, `MAX_QUERY_LENGTH`, `MAX_EXPANDED_TERMS`, `OLLAMA_TIMEOUT_MS`, `HEALTH_CHECK_TIMEOUT_MS`, `MAX_REQUEST_BODY_BYTES`, `INDEX_REQUEST_TIMEOUT_MS`, `POOL_QUEUE_CAPACITY`, `MAX_CONCURRENT_CONNECTIONS`, `SHUTDOWN_TIMEOUT_MS` задаються конфігурацією (змінні оточення), а не константами в коді.
- **Обґрунтування:** `.claude/rules/code-quality.md` §11.
- **Джерело:** P.
- **Пріоритет / Походження:** Must / P (від неї залежать Must-вимоги FR-003, NFR-020).
- **Критерії:** Кожен параметр зі списку має змінну оточення, значення за замовчуванням і валідацію при старті; некоректне значення → сервер не стартує і пише зрозуміле повідомлення; `.env.example` містить усі параметри.
- **Перевірка:** T — TEST-UT-12, I.
- **Залежності:** —

### NFR-021. Відсутність секретів і межа відкритості

## Експлуатація (доповнення після аудиту раунду 1)

### NFR-024. Готовність моделі Ollama після запуску
- **Категорія:** Portability / Availability.
- **Опис:** Після `docker compose up` налаштована модель Ollama стає доступною без ручних дій, і query expansion працює.
- **Обґрунтування:** Інакше критерій «Query expansion» не виконується після запуску «однією командою» (AUD-1-04).
- **Джерело:** SRC-A §Основні вимоги п.2, п.5; спосіб завантаження моделі — P (OQ-13).
- **Пріоритет / Походження:** Must / P.
- **Критерії:** Зі свіжого клону (з порожнім томом моделі) після `docker compose up` протягом `READINESS_TIMEOUT_S` (OQ-13): health → `ollama: true`; WS-запит з таблиці тестових запитів дає непорожні `expanded_terms`. Повторний запуск використовує збережену модель без повторного завантаження.
- **Перевірка:** T — TEST-E2E-07.
- **Залежності:** NFR-011, FR-002, FR-019.

### NFR-025. Обмеження одночасних з'єднань
- **Категорія:** Resource utilization / Availability.
- **Опис:** Кількість одночасно оброблюваних з'єднань (HTTP і WebSocket) обмежена `MAX_CONCURRENT_CONNECTIONS`; понад ліміт сервер відповідає явно, а не вичерпує ресурси.
- **Обґрунтування:** `.claude/rules/architecture.md` §10 (resource limits, backpressure); бенчмарк throughput може перевищити можливості сервера.
- **Джерело:** P (OQ-35).
- **Пріоритет / Походження:** Should / P.
- **Критерії:** `GET /api/health` не підпадає під ліміт і завжди обслуговується (FR-001). M (P, OQ-35) більше за максимальну кількість клієнтів K бенчмарку NFR-003, щоб бенчмарк не отримував 503. При `MAX_CONCURRENT_CONNECTIONS` = M і M + 5 одночасних довгих з'єднаннях (WS-сесії з затримкою Ollama): перші M обслуговуються; надлишкові HTTP-запити отримують 503 `server_busy`, надлишкові WS-рукостискання відхиляються з HTTP 503; процес сервера продовжує працювати; після звільнення з'єднань нові запити обслуговуються.
- **Перевірка:** T — TEST-RES-04.
- **Залежності:** FR-028, NFR-019.

### NFR-026. Коректне завершення сервера
- **Категорія:** Reliability.
- **Опис:** За сигналом завершення (SIGTERM від `docker compose down`/`stop`) сервер припиняє приймати з'єднання, закриває WebSocket-сесії з кодом 1001, перериває побудову без активації нового індексу (P, OQ-32; клієнт `POST /api/index` отримує закриття з'єднання без відповіді), завершує пули потоків і виходить з кодом 0 у межах `SHUTDOWN_TIMEOUT_MS`.
- **Обґрунтування:** Без цього Docker вбиває процес через SIGKILL, а потоки і ресурси не звільняються (`.claude/rules/architecture.md` §6).
- **Джерело:** P (OQ-32).
- **Пріоритет / Походження:** Should / P.
- **Критерії:** Під час активної WS-сесії і побудови надсилається SIGTERM: клієнт отримує закриття 1001; процес виходить з кодом 0 за ≤ `SHUTDOWN_TIMEOUT_MS`; у лозі немає повідомлень про аварійне завершення.
- **Перевірка:** T — TEST-RES-05.
- **Залежності:** FR-040.

### NFR-027. Безпечність пам'яті
- **Категорія:** Reliability / Maintainability.
- **Опис:** Модульні, інтеграційні, API- і WS-тести проходять у збірці з AddressSanitizer і UndefinedBehaviorSanitizer без звітів.
- **Обґрунтування:** Ручне керування пам'яттю в C++ (ADR-001, наслідки); `.claude/rules/testing.md` §5, §11. Помилки пам'яті (use-after-free, вихід за межі власних масивів CON-015) роблять недостовірною перевірку гонок NFR-004 і критерію CC-05.
- **Джерело:** P (необхідна для NFR-004 / CC-05).
- **Пріоритет / Походження:** Must / P.
- **Критерії:** Прогін наборів UT, IT, API, WS у збірці `-fsanitize=address,undefined` завершується без звітів санітайзерів і з усіма тестами пройденими.
- **Перевірка:** T — TEST-DOC-09.
- **Залежності:** —
