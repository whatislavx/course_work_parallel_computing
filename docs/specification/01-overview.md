## 1.3. Постановка задачі

Потрібно дослідити та реалізувати паралельні обчислення на прикладі пошукової системи (SRC-A, «Назва роботи»). Система має:

- паралельно будувати інвертований індекс за допомогою власного пулу потоків і власної потокобезпечної структури даних;
- одночасно обробляти запити від кількох клієнтів;
- розширювати пошукові запити через локально розгорнуту LLM (Ollama);
- надавати результати через REST API та WebSocket;
- мати два клієнти: консольний і веб;
- запускатися однією командою `docker compose up`;
- супроводжуватися дослідженням масштабованості (графіки, аналіз вузьких місць).

## 1.4. Бачення продукту

Контейнеризована навчальна пошукова система, на якій можна виміряти й показати ефект паралелізму на кожному етапі: побудова індексу (пул потоків + потокобезпечний індекс), обробка запитів кількох клієнтів, пайплайн пошуку `query_expansion → keyword_search → done`.

## 1.6. Межі (scope)

**У межах:**

- пошуковий сервер на C++ (ADR-001) з REST API та WebSocket;
- власний пул потоків і власний потокобезпечний інвертований індекс;
- інтеграція з Ollama через `/api/generate`;
- CLI-клієнт і Web UI;
- `docker-compose.yml` з сервісами пошукового сервера та Ollama;
- скрипти бенчмарків і графіки;
- набір даних (отримання або генерація) та його перевірка;
- проєктна документація: UML, README, пояснювальна записка.

**Поза межами:**

| ID | Що не робимо | Причина |
|---|---|---|
| OOS-1 | Режими пошуку, крім `keyword` (семантичний, векторний) | SRC-A визначає лише `mode: keyword` |
| OOS-2 | Автентифікація, авторизація, ліміти запитів | Не вимагається; система навчальна й локальна |
| OOS-3 | Збереження індексу між перезапусками | Не вимагається (пропозиція, OQ-26) |
| OOS-4 | Розподілена (багатовузлова) побудова індексу | Не вимагається |
| OOS-5 | Інкрементальне оновлення індексу (додавання окремих документів) | Не вимагається; індекс будується повністю |
| OOS-6 | Версіонування API (`/v1`) | Контракт фіксований SRC-A |
| OOS-7 | Генерація відповідей LLM (RAG), підсумовування | SRC-A вимагає лише query expansion |
| OOS-8 | Підготовка відповідей на теоретичні питання (SRC-B) | Не програмна вимога; відстежується в матриці A як поза ПЗ |

## 1.8. Терміни та визначення

| Термін | Визначення |
|---|---|
| Документ | Одиниця індексації. Пропозиція: один текстовий файл датасету = один документ (OQ-18) |
| `doc_id` | Рядковий ідентифікатор документа в результатах. Пропозиція: шлях файлу відносно кореня датасету (OQ-18) |
| Терм | Нормалізований токен тексту (правила токенізації, OQ-21) |
| Постинг | Запис «документ + частота терма в ньому» |
| Інвертований індекс | Відображення терм → список постингів |
| Пул потоків (thread pool) | Фіксований набір робочих потоків із чергою задач, реалізований власноруч |
| Query expansion | Доповнення запиту ключовими словами та синонімами, отриманими від LLM |
| Пайплайн пошуку | Послідовність етапів `query_expansion` → `keyword_search` → `done` |
| Етап (stage) | Одне повідомлення WebSocket з полями `stage` і `data` |
| Розширені терміни | Масив `expanded_terms` у даних етапу `query_expansion` |
| `T(p)` | Медіанний час побудови індексу з `p` потоками |
| Прискорення | `S(p) = T(1) / T(p)` |
| Ефективність | `E(p) = S(p) / p` |
| Throughput | Успішні запити / загальний час бенчмарку |
| Fallback | Поведінка за недоступності Ollama: пошук за початковим запитом без розширення |
| Обов'язкова вимога | Вимога, що прямо випливає з SRC-A/SRC-SYL (позначка **M**) |
| Запропонована вимога | Вимога, якої немає в SRC-A, але без якої поведінка невизначена; очікує затвердження (позначка **P**) |

## 1.9. Пріоритети

| Пріоритет | Значення |
|---|---|
| Must | Обов'язково для зарахування критерію SRC-SYL або прямо вимагається SRC-A |
| Should | Потрібно для коректної та захищеної системи, але критерію оцінювання не відповідає напряму |
| Could | Бажано, якщо залишиться час |

Кожна вимога має два атрибути: **Пріоритет** (Must/Should/Could) і **Походження** (M — обов'язкова з SRC, P — запропонована, очікує рішення).

Правило поєднання **Must / P**: вимоги немає в SRC, але без неї неможливо реалізувати або перевірити Must-вимогу з SRC (наприклад, fallback FR-021 для критерію query expansion, поведінка пулу FR-038…FR-041 для критерію thread pool). Пріоритет Must у такому разі означає «необхідна», а не «прямо вимагається»; конкретне рішення залишається пропозицією до закриття відповідного OQ. Must-вимога не може залежати від Should-вимоги; якщо така залежність виникає, залежність підвищується до Must.
