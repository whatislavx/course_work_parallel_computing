# Глосарій проєкту «Курсова: паралельні обчислення»

Терміни згруповано за темами. Скорочення, які зустрічаються в специфікації (`docs/specification/`), подано з посиланням на джерело.

## Методологія і документи

- **SDD (Specification-Driven Development)** — розробка, у якій специфікація є джерелом істини для реалізації. Етапи: Discovery → Specification → Architecture → Planning → Implementation → Verification → Documentation (CLAUDE.md §3).
- **SRS (Software Requirements Specification)** — специфікація вимог за IEEE 29148, набір файлів `docs/specification/01…13` плюс `openapi.yaml`.
- **SRC-SYL / SRC-A / SRC-B** — джерела: силабус курсу, завдання курсової (Додаток A), питання захисту (Додаток B).
- **CC-01…CC-23** — критерії курсової з матриці A (`10`): автоматичні бали, захист, атестації, Git, записка тощо.
- **Матриці A–E** (`10-requirements-traceability.md`): A — критерії → вимоги; B — вимоги → BDD → тести; C — залежності між вимогами; D — вимоги → API; E — вимоги → тікети.
- **BDD (Behavior-Driven Development)** — сценарії поведінки у форматі Gherkin, файл `05`. Теги на зразок `BDD-IDX-01`.
- **Gherkin / Scenario Outline** — синтаксис BDD-сценаріїв; Outline з таблицею Examples для варіантів одного правила.
- **AC (acceptance criterion)** — критерій прийняття, наприклад `AC-001.1` (код 200 для health).
- **DoD (Definition of Done)** — загальні умови завершення тікета (`10`, матриця E).
- **Baseline (SRS baseline)** — затверджена версія специфікації, від якої починається реалізація.
- **Change log** — журнал версій специфікації (`13`).

## Вимоги і їх типи

- **FR (Functional Requirement)** — функціональна вимога, `FR-001…FR-043`.
- **NFR (Non-Functional Requirement)** — нефункціональна вимога, `NFR-001…NFR-027` (продуктивність, надійність, конфігурованість, код і т. ін.).
- **CON (Constraint)** — обмеження, наприклад `CON-001` (мова C++20, CMake, GoogleTest, Boost), `CON-015` (власна структура даних).
- **DEL (Deliverable)** — обов'язковий результат здачі, наприклад `DEL-07` (графіки), `DEL-12` (пакет першої атестації).
- **OOS (Out of Scope)** — поза межами проєкту, наприклад `OOS-2` (автентифікація немає).
- **Must / Should / Could** — пріоритет вимоги: обов'язкова, бажана, опційна.
- **Методи перевірки:** T — тест, A — аналіз вимірювань, I — інспекція, D — демонстрація.
- **Статуси:** «Специфіковано» — сценарій і тест визначено, але не реалізовано; «Перевірено» — підтверджено запуском.

## Рішення та відкриті питання

- **OQ (Open Question)** — відкрите питання, `OQ-01…OQ-38` (`12-open-questions.md`). Статуси: Resolved, Open, Pending.
- **AD (Architecture Decision)** — архітектурне рішення, `AD-01…AD-11`, затверджене власником. Приклади: AD-03 — стек (C++20, CMake, GoogleTest, Boost.Beast, Boost.JSON); AD-07 — Web UI в окремому контейнері; AD-10 — власні структури даних.
- **DEV (Deviation)** — відхилення від SRC-A, `DEV-01…DEV-04`. DEV-02 скасовано (AD-07).
- **Позначки в тексті:** `[P]` — пропозиція, що потребує затвердження; `B` — блокувальне рішення; `Superseded` — замінено іншим рішенням.
- **Власник (owner)** — людина, яка приймає остаточні рішення: технології, архітектуру, зміни вимог, коміти, пуш (CLAUDE.md §2, §6).

## Архітектура і технології

- **Інвертований індекс (inverted index)** — структура «термін → список документів, де він є» (постинги). Основа пошуку.
- **Постинг (posting)** — запис про входження терміну в документ (`doc_id`, частота тощо).
- **Власна структура даних** — індекс і черга пулу реалізовані вручну поверх масивів і списків. Заборонені асоціативні та множинні контейнери і `std::hash` (AD-10, CON-015).
- **Пул потоків (thread pool)** — власний пул для побудови індексу з `p` робочими потоками (AD-04, CON-003). Клієнтські запити обробляють потоки Boost.Beast.
- **Паралельна побудова (parallel build)** — побудова індексу розподіленими задачами по пулу.
- **Ранжування (ranking)** — порядок результатів пошуку за формулою з OQ-04.
- **Snippet** — фрагмент документа навколо терміна пошуку (FR-015).
- **Query expansion (розширення запиту)** — додавання синонімів або пов'язаних термінів через LLM. Режим `expanded` у REST, етап у WebSocket.
- **Ollama** — локальний сервер LLM. Використовується ендпоінт `/api/generate`. Модель мала, завантажується скриптом (AD-06).
- **Fallback** — якщо Ollama недоступна або не відповіла вчасно, розширених термінів немає, `expanded_terms: []` (FR-021).
- **REST API** — HTTP-інтерфейс: EP-01 `GET /api/health`, EP-02 `POST /api/index`, EP-03 `POST /api/search`, EP-04 `GET /api/stats` (`06`, `openapi.yaml`).
- **WebSocket pipeline** — `/ws/search`, етапи `query_expansion → keyword_search → done` (WS-E-01…WS-E-04).
- **Подія `done`** — завершальне повідомлення без поля `data` (AD-09).
- **Health (health check)** — `GET /api/health`, показує, що сервер працює (`status: ok`), і доступність Ollama (`ollama: true/false`).
- **Формат помилки** — `{"error":{"code","message"}}` (06 §2.4, AD-05). Приклади кодів: `not_found` (404), `method_not_allowed` (405), `payload_too_large` (413), `index_not_ready` (409), `server_busy` (503).
- **Коди стану** — 200, 400, 404, 405, 409, 413, 500, 503 (06 §2.3).
- **Time_ms** — тривалість побудови від виявлення документів до активації нового індексу (AD-08).
- **Активація індексу** — атомарна заміна старого індексу новим після успішної побудови (FR-008).
- **Стани індексу** — Empty / Building / Ready / Rebuilding (TCK-012).
- **Web UI** — веб-інтерфейс у окремому контейнері, який проксіює `/api` і `/ws/search` (AD-07).
- **CLI** — командний клієнт `./search "запит"` (FR-029, FR-030).
- **Docker Compose** — оркестрація сервісів: сервер, ollama, web (NFR-012).
- **Path traversal** — атака з `../` для доступу поза каталогом статики. Захист має повертати 404 (NFR-021, TEST-RES-03).

## Інструменти і технології

- **C++20** — мова бекенду (AD-03, ADR-001).
- **CMake** — система збирання.
- **GoogleTest** — тестовий фреймворк.
- **Boost.Beast** — HTTP, WebSocket і HTTP-клієнт для Ollama (AD-03).
- **Boost.JSON** — розбір і формування JSON (AD-03).
- **-Werror** — попередження компілятора вважаються помилками.
- **TSan (ThreadSanitizer)** — виявляє гонки даних; збірка проходить з нульовими звітами.
- **ASan / UBSan (AddressSanitizer / UndefinedBehaviorSanitizer)** — пам'ять і невизначена поведінка.
- **clang-format / clang-tidy** — форматування і статичний аналіз.
- **Conventional Commits** — формат повідомлень комітів (`feat:`, `docs(spec):` тощо).
- **Attribution lines** — службові рядки в комітах (`Co-Authored-By`, `Claude-Session`).

## Продуктивність і дослідження

- **T(p)** — час побудови індексу з `p` потоками.
- **S(p) = T(1) / T(p)** — прискорення (speedup).
- **E(p) = S(p) / p** — ефективність паралелізму.
- **Throughput** — кількість запитів за секунду при навантаженні (NFR-003).
- **RSS (Resident Set Size)** — пам'ять процесу, яку вимірюють під час побудови.
- **Закон Амдала** — межа прискорення через послідовну частину програми (аналіз вузьких місць, TCK-031).
- **Бенчмарк** — скрипт вимірювань, який видає CSV і графіки (TCK-029, TCK-030).
- **Датасет** — набір документів для тестування. Не менше 10 000 документів (CC-21, NFR-014). Джерело — OQ-01, очікує викладача.
- **Фікстури (FIX-01…FIX-06)** — тестові дані: корпус, еталон, таблиця запитів, двійник Ollama, генератор «повільного» корпусу (TCK-035).

## Тікети і процес

- **TCK-001…TCK-042** — тікети реалізації (`10`, матриця E). Перенесені в GitHub issues з префіксом у назві `TCK-0xx`.
- **Етапи M0–M6** — групи тікетів: M0 рішення, M1 перша атестація, M2 індекс і паралелізм, M3 пошук і REST, M4 LLM і WebSocket, M5 клієнти, M6 дослідження і здача.
- **Атестація** — проміжна перевірка викладачем: перша (тижні 7–8: compose, health, UML use case, class, sequence) і друга (готовий продукт).
- **Протокол тестування (DEL-15)** — документ з результатами запуску тестів.
- **Пояснювальна записка** — письмовий звіт із 5 розділів і графіками (DEL-09…DEL-11).
- **Захист** — усна презентація з відповідями на теоретичні питання (CC-12…CC-14).
- **Ревю субагентом** — незалежна перевірка коду окремим агентом (зазвичай на Opus) без доступу до процесу написання.
